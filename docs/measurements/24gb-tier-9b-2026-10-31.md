# 24 GB tier: Qwen3.5 9B instead of Qwen3.6 35B-A3B Q3 (2026-10-31)

## Decision

From 0.3.18, Macs in the 24 GB memory class get the same model and profile as 16 GB Macs: Qwen3.5 9B Q4_K_M,
16K context, medium thinking, `ctx-checkpoints 4`, `cache-ram 0` (`ModelSelector.table` in
`app/Sources/PippaCore/Models.swift`). Macs with 32 GB and more keep Qwen3.6 35B-A3B UD-Q3_K_XL without thinking.
The hidden "More thorough" row (35B-A3B IQ3) is unchanged and stays hidden.

The reason is memory, not answer quality. The 35B needs 17.5 GiB of a 24 GB Mac. Pippa's rule is that she must
never freeze the Mac, and on the 24 GB test Mac the 35B profile did not meet that bar.

This change is **not released until the gate below has passed on a real 24 GB Mac**.

## Evidence

| | Qwen3.5 9B Q4, medium | Qwen3.6 35B-A3B Q3, thinking off |
|---|---|---|
| Source | [model-compare](model-compare/README.md), 2026-10-09 | [qwen-gguf-validation](qwen-gguf-validation-2026-10-24/README.md), 2026-10-24 |
| Ten Pippa tasks | 17 yes / 12 partial / 1 no, from 30 runs (10 tasks × 3 rounds), rubric graded by hand | 6 of 10 passed, one run, manual pass/fail |
| Median time per task | 22.7 s warm (27.8 s over all runs) | 34.5 s |
| Context in that run | 32K | 32K |
| Model memory (catalog `memGiB`) | 7 GiB | 17.5 GiB |
| llama-server peak RSS | about 8.0 GB (7.6–9.0) | not measured in the same way |
| Invented facts (hand count) | 2 of 30 | not counted in the same way |
| Blind German rating (1–5) | 3.83, best of the three variants | not rated |
| Long context on a 24 GB Mac | not measured | a 30,044-token request took 163.8 s; system swap was already at 8.2 GiB and grew to 8.4 GiB |
| Download | 5.68 GB | 16.85 GB |

## Caveats

- **Not a controlled comparison.** The ten task names are the same, but the two runs used different Pippa code,
  different graders and rules (a yes/partial/no rubric over three rounds versus a stricter single-run pass/fail),
  different time limits and different days. "17 yes of 30" and "6 of 10" can't be set against each other as rates.
  The claim here is only that the 9B did well enough on these tasks, not that it beats the 35B.
- **The shipped 24 GB profile wasn't run as such.** model-compare ran the 9B at 32K context. The shipped profile is
  16K with `cache-ram 0` and four context checkpoints, the profile 16 GB Macs already use. Nobody has run it through
  the ten tasks on a 24 GB Mac yet.
- **The swap reading is weak evidence on its own.** Swap was already high before the 30K request, the desktop load
  was not controlled, and process footprint counters miss part of the GGUF/Metal memory. It is enough to say the 35B
  leaves no room on a busy 24 GB Mac. It doesn't measure how much room the 9B leaves.
- **Losses are possible.** The 35B might answer some tasks better than the 9B. The data does not settle that either
  way.

## Existing 24 GB installations

When a 24 GB Mac updates from 0.3.17 with the 35B set up:

- Setup asks the usual single download question for the 9B (5.7 GB), unless LM Studio, Ollama or Hugging Face already
  has the exact file, in which case Pippa adopts it without a download. `models.json` names the 9B right away, so
  Pippa never quietly keeps answering with the 35B. This works because `PiSetupFlow.fallback` skips a previous model
  that the table now gives only to larger Macs (`ModelSelector.isForLargerMacs`). Before this change it would have
  kept the 35B running and offered the 9B only in Settings and the menu bar.
- Pippa doesn't delete the 35B file. It is still a table model (32 GB and up), so `SupersededModels` never removes
  it. Freeing the 16.8 GB is the person's call.
- An explicit `localModelKey` or `PIPPA_PI_MODEL` naming the 35B still wins, as for any explicit choice, with a 16K
  context.
- Until setup has run once after the update, the terminal launch file (`pippa-local-server.json`) can still name the
  35B. Setup rewrites it once the 9B is ready.
- Checks: PippaChecks "Setup: 24 GB update from the 35B → the download question for the 9B, models.json names the
  9B, the 35B file stays" and "Model: the 35B is for 32 GB and up only …".

## Release gate (run by the owner on a 24 GB Mac)

Use a 24 GB Apple-silicon Mac in normal use: Safari with several tabs, Mail and Pages open. Don't use a developer's
working machine that is busy with builds. Use a signed 0.3.18 build that has the 9B set up through the normal
download.

1. **Swap.** Record `sysctl vm.swapusage` and the llama-server footprint before the first question. Run the ten
   Pippa tasks, then one request with about 15K tokens of context (the profile's limit). Pass: swap grows by at most
   256 MiB, no beach ball, and the other apps stay responsive.
2. **Ten tasks.** Run the ten model-compare tasks with production sampling and grade them by hand under the same
   rubric as model-compare. Pass: at least 16 yes from 30 runs (one fewer than model-compare's 17, for the smaller
   context) and no task that is "no" in all three rounds.
3. **Time.** The median time per task stays at or below 34.5 s, the 35B's time.

If any step fails, 0.3.18 ships with the 24 GB row back on the 35B (one line in `ModelSelector.table`), and this
record says what failed. The results go into this file under a new "Gate result" heading with the date, the Mac
model and the build number.
